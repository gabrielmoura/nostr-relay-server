= NRServer - Documentacao Tecnica Principal
:toc:
:toclevels: 4

Este documento e a referencia tecnica principal do projeto `nostr-relay-server`.
Ele cobre arquitetura, funcionamento interno, contratos, configuracao, operacao e manutencao.

== 1. Escopo e publico alvo

Publico alvo:

* maintainers
* desenvolvedores backend (Go)
* operadores de ambiente
* contribuidores que precisam entender fluxos internos

Objetivos:

* onboarding tecnico rapido
* entendimento de arquitetura e fluxo de execucao
* guia operacional para desenvolvimento e producao
* base para evolucao da documentacao viva

== 2. Visao tecnica do sistema

=== 2.1 Proposito

`nrserver` e um relay Nostr orientado a operacao, com:

* transporte WebSocket para protocolo Nostr
* persistencia em PostgreSQL
* cache/pubsub opcional via Redis
* suporte opcional a grupos NIP-29
* pipeline de ingestao em lote com backpressure
* APIs administrativas internas
* API opcional de gerenciamento NIP-86 na raiz publica
* metricas Prometheus
* sincronizacao Negentropy

=== 2.2 Responsabilidades principais

Responsabilidades core:

* receber mensagens Nostr (`EVENT`, `REQ`, `COUNT`, `AUTH`, `CLOSE`, `NEG-*`)
* validar politicas de evento e request (incluindo Web of Trust e Listas de Kinds)
* persistir eventos de forma segura e eficiente
* notificar subscribers locais e distribuidos
* opcionalmente federar eventos/requests para relays externos
* opcionalmente manter estado de grupos NIP-29 e emitir eventos relay-owned `39000`-`39003`

Responsabilidades auxiliares:

* proxy WebSocket (`proxy`) multiplexador com alta vazao e deduplicacao (`bostr2` style)
* import/export/download/sync via CLI
* jobs de manutencao (`cron`)
* bootstrap de dados iniciais (`seed --bootstrap`)

Responsabilidades administrativas:

* endpoints `/admin/*` para observabilidade, moderacao, sincronizacao e gerenciamento de grupos/WoT
* painel web embedado em `/panel`
* endpoint opcional NIP-86 JSON-RPC em `/` com autenticacao NIP-98

=== 2.3 Topologia de runtime

O processo sobe dois servidores Fiber:

* externo: `port` (relay publico)
* interno: `port+1` (admin + metrics + panel)

Endpoints principais:

* externo: `/` (NIP-11 + upgrade WS + NIP-86 opcional), `/.well-known/*`, `/upload`, `/blob/:id`, `/list/:id`
* interno: `/metrics`, `/admin/*`, `/panel/*`

== 3. Arquitetura e modulos

=== 3.1 Estrutura de alto nivel

* `cmd/`: superficie CLI (Cobra)
* `cmd/internal/`: logica de execucao por comando
* `config/`: modelo, defaults e loader de configuracao
* `infra/net/`: construcao de servidores e rotas Fiber
* `infra/handler/`: handlers HTTP/WS e use-cases de transporte
* `infra/ingestion/`: pipeline batch de ingestao
* `infra/stream/`: dispatcher async de federacao
* `infra/db/`: queries e migracao SQL
* `internal/policies/`: hub unico de politicas
* `internal/wot/`: mecanismo otimizado O(1) do Web of Trust (Trust Graph)
* `internal/groups/`: runtime opcional de grupos NIP-29
* `pkg/negentropy*`: reconciliacao de sincronizacao
* `pkg/nostrpool/`: relay pool para stream up/down

=== 3.2 Dependencias tecnicas centrais

* CLI: `spf13/cobra`
* HTTP: `gofiber/fiber/v2` + `gofiber/contrib/websocket`
* DB: `pgx/v5` + `pgxpool`
* Config: `spf13/viper`
* Nostr: `nbd-wtf/go-nostr`
* Logging: `uber-go/zap`
* Metrics: `prometheus/client_golang`
* Redis: `go-redis/v9` (encapsulado em `infra/redis`, `infra/cache`, `infra/pubsub`)

== 4. Ciclo de inicializacao e shutdown

=== 4.1 Entry point

Fluxo de boot do binario:

1. `cmd/nrserver/main.go` chama `cmd.Execute()`
2. `cmd/root.go` executa o comando Cobra selecionado
3. `cmd/server.go` (comando `server`) inicia runtime completo

=== 4.2 Sequencia de boot do comando `server`

Sequencia observada em `cmd/server.go`:

1. carrega `conf.yaml` via `config.LoadConfig()`
2. inicializa logger (`infra/log`)
3. cria `mainCtx` com cancelamento
4. inicializa Redis (falha nao e fatal)
5. inicializa cache/pubsub/listener
6. inicializa conexao DB (falha e fatal)
7. tenta prepared statements em `production` (falha nao e fatal)
8. registra metricas
9. inicializa modulo opcional NIP-29
10. inicializa hub de politicas
11. inicia ingestion workers e stream dispatcher
12. constroi apps Fiber interno/externo (`infra/net.Router()`)
13. inicializa relay pool se stream up/down habilitado
14. opcionalmente executa bootstrap de eventos
15. aplica override persistido de metadata do relay (quando existir)
16. abre listeners TCP em `port+1` e `port`
17. bloqueia aguardando `mainCtx.Done()`

=== 4.3 Shutdown

Sinais tratados: `SIGINT` e `SIGTERM`.

Quando sinal recebido:

* cancela contexto principal
* para ingestion
* fecha pubsub
* executa shutdown dos dois apps Fiber
* fecha cliente Redis

Observacao tecnica: o fechamento do pool PostgreSQL e indireto pelo ciclo de vida do processo e componentes DB.

== 5. Funcionamento interno

=== 5.1 Conexao WebSocket

`RootUpgrade` (`infra/handler/http/root.go`) faz:

* resposta NIP-11 quando `Accept: application/nostr+json`
* branch opcional NIP-86 quando `Content-Type: application/nostr+json+rpc`
* upgrade WS quando aplicavel
* injeta `dto.WsServer` em `Locals("wss")`

`HandleConnection` (`infra/handler/ws/connection.go`) faz:

* ticker de ping/pong
* atualizacao de presenca em listener
* envio de AUTH challenge conforme modo de auth
* loop de escrita (`ChanSender`, `ChanPing`, ping periodico)
* loop de leitura com limite de mensagem (`1 MiB`)

=== 5.2 Roteamento de mensagens WS

Router em `infra/handler/ws/message_router.go`:

* decode defensivo + `recover` para evitar panic derrubar conexao
* metricas por tipo (`NostrRequestCounter`)
* dispatch por tipo:
  - `EVENT` -> `infra/handler/event`
  - `REQ` -> `infra/handler/req`
  - `COUNT` -> `infra/handler/count`
  - `AUTH` -> `infra/handler/auth`
  - `CLOSE` -> remove subscription
  - `NEG-*` -> `pkg/negentropy` (se habilitado)

=== 5.3 Pipeline de ingestao

`infra/ingestion/ingestion.go` implementa pipeline batch:

* fila bufferizada (`queue_size`)
* workers concorrentes (`workers`)
* flush por tamanho (`batch_size`) ou timeout (`batch_timeout_ms`)
* deduplicacao (`cache.SetDedup`)
* validacao storage-safe via `policies.ValidateBatchEvent`
* semantica replaceable/addressable antes de persistir
* persistencia em lote (`InsertEventBatch`)
* fan-out: notify listeners, stream forward, pubsub publish, cache de evento

Backpressure:

* se fila cheia, `Push` retorna `false`
* incrementa metrica de backpressure

=== 5.4 Forwarding assincromo (stream)

`infra/stream/stream.go`:

* dispatcher com duas filas:
  - `eventQueue` (upstream)
  - `reqQueue` (downstream backfill)
* workers dedicados para evento e request
* filas bounded e contadores de drop
* allowlist de kinds para upstream

Comportamento:

* `stream_up=true`: publica eventos no relay pool
* `stream_down=true`: consulta pool para REQ sem depender do caminho sincrono do handler

=== 5.5 Hub de politicas

`internal/policies/hub.go` concentra validacoes:

Para EVENT/BATCH:

* id hash valido
* validacao no grafo em memoria de Web of Trust (WoT) configuravel
* fitragem rigorosa por `WhitelistKinds` e `BlacklistKinds`
* assinatura valida
* ban check
* tamanho maximo
* expiracao (`expiration`)
* POW minimo
* limites de tags
* bloqueio de base64 inline
* regras NIP-29 para grupos, permissao, convite, PoW e `previous` quando habilitado

Para REQ/COUNT:

* normalizacao de limit
* ban check para requisitante autenticado
* regras de auth por modo
* bloqueio de filtro vazio (se configurado)
* anti-sync-bot
* regras para kinds protegidos e DM

== 6. Especificacoes tecnicas e contratos

=== 6.1 Protocolos suportados

NIPs/BUDs suportados estao documentados em `README.md` e `docs/api-spec.md`.
No runtime, os contratos principais incluem:

* NIP-01 envelopes WS (`REQ`, `EVENT`, `EOSE`, `OK`, `NOTICE`, `CLOSED`)
* NIP-13 para validacao opcional de POW em grupos NIP-29
* NIP-11 relay information no endpoint raiz HTTP
* NIP-86 relay management via JSON-RPC sobre HTTP no endpoint raiz
* NIP-29 relay-based groups com kinds `9000`-`9009`, `9021`, `9022`, `39000`-`39003`
* NIP-42 auth challenge/response
* NIP-45 (`COUNT`)
* NIP-96 upload/download de blobs
* Negentropy (`NEG-OPEN`, `NEG-MSG`, `NEG-CLOSE` e compatibilidade legada)

=== 6.2 Contrato WS (entrada)

Entrada esperada (JSON array):

[source,json]
----
["REQ", "<subscription_id>", {"kinds":[1],"authors":["<pubkey>"]}]
["EVENT", {"id":"...","pubkey":"...","kind":1,"tags":[],"content":"...","sig":"..."}]
["COUNT", "<subscription_id>", {"kinds":[1]}]
["AUTH", {"kind":22242, ... }]
----

=== 6.3 Contrato WS (saida)

[source,json]
----
["EVENT", "<subscription_id>", { ...event... }]
["EOSE", "<subscription_id>"]
["OK", "<event_id>", true, "saved"]
["NOTICE", "<reason>"]
["CLOSED", "<subscription_id>", "<reason>"]
----

=== 6.4 Contrato HTTP interno/admin

Auth:

* se `admin_token` vazio -> endpoints admin sem token
* se `admin_token` definido -> exigir `X-Admin-Token`

Conjuntos de endpoint:

* overview/status: `/admin/overview`, `/admin/stream/status`
* conexoes: `/admin/connections/*`
* usuarios/moderacao: `/admin/users/*`
* eventos/search/import/fetch/reports/download: `/admin/events/*`
* sincronizacao: `/admin/sync/*` (Negentropy)
* grupos NIP-29: `/admin/groups/*`
* Web of Trust: `/admin/wot/*` (summary e trusted pubkeys)
* NIP-86 interno para o dashboard: `/admin/nip86/*`
* painel: `/panel` e `/panel/*`

=== 6.5 Contrato HTTP externo

* `/` com `Accept: application/nostr+json` -> relay info
* `/` com `Content-Type: application/nostr+json+rpc` -> NIP-86 opcional
* `/` com upgrade WS -> sessao Nostr
* `/.well-known/nostr/nip96.json`
* `/.well-known/nostr.json`
* `/upload`, `/blob/:id`, `/list/:id` (Blossom)

=== 6.6 Contrato NIP-86 (externo e opcional)

Quando habilitado:

* endpoint: `POST /`
* content-type obrigatorio: `application/nostr+json+rpc`
* auth obrigatoria via NIP-98 (`kind:27235`)
* `payload` obrigatorio com SHA-256 do corpo JSON-RPC
* somente a `pubkey` configurada em `admin_pubkey` pode executar metodos

Metodos suportados atualmente:

* `supportedmethods`
* `banpubkey`, `unbanpubkey`
* `allowpubkey`, `unallowpubkey`
* `banevent`, `allowevent`
* `blockip`, `unblockip`
* `changerelayname`, `changerelaydescription`

=== 6.7 Limitacoes conhecidas

* limite hard de mensagem WS: `1 MiB`
* cron usa expressoes com 6 campos (segundos incluidos)
* `db.postgres_uri` e obrigatorio
* stream upstream possui allowlist de kinds, nao e forwarding irrestrito
* NIP-86 e desabilitado por padrao e exige `admin_pubkey` + `relay_information.url`
* `blockip` derruba imediatamente apenas conexoes conhecidas pelo processo local

== 7. Funcionalidades (por categoria)

=== 7.1 Core

* relay WS Nostr
* validacao por politicas
* ingestao batch com dedup e semantica replaceable/addressable
* persistencia PostgreSQL

=== 7.2 Auxiliares operacionais

* `seed` para migracao/bootstrap
* `proxy` para instanciar sub-processos lightweight que consultam upstreams (`Stream.Relays`)
* `import` e `export` (jsonl/tsv)
* `download` com filtro JSON e merge strategy
* `sync` com Negentropy e filtros
* `cron` para manutencao periodica

=== 7.2 Grupos NIP-29 (opcional)

Quando `nip29.enabled=true`:

* cria e atualiza estado de grupos em tabelas `nip29_*`
* valida `h` tag, permissao e visibilidade de leitura/escrita
* emite eventos relay-owned `39000`, `39001`, `39002`, `39003`
* suporta convites por codigo com `kind:9009`
* suporta PoW por grupo ou por moderacao
* suporta validacao de timeline references via tag `previous`
* usa Redis como acelerador de hot path para membership, bans, invites, metadata e timeline recente

=== 7.3 Administrativas

* visao de conexoes ativas/authed
* moderacao de usuarios (ban/unban)
* busca e agregacoes de eventos
* fetch/download massivo de eventos em relays externos
* sincronizacao reconciliada via Negentropy
* gerenciamento de grupos NIP-29 e Web of Trust (WoT) via dashboard
* painel web interno embedado

== 8. Configuracao tecnica

=== 8.1 Origem e lookup

`config.LoadConfig()` busca `conf.yaml` em:

1. `.`
2. `../..`
3. `/etc/nrs`

=== 8.2 Defaults e campos obrigatorios

* defaults definidos em `config/defaults.go`
* `db.postgres_uri` obrigatorio (falha no load se vazio)
* fallback de `app_env`: `production`
* `nip86.enabled=true` exige `admin_pubkey`, `relay_information.url`, `auth_window_seconds>0` e `cache_ttl_seconds>0`

=== 8.3 Blocos principais e impacto operacional

* `ws.*`: auth mode e rate-limit de conexoes
* `relay.*`: limites, tamanho, POW, whitelist/blacklist de kinds
* `wot.*`: controles e limits pro background goroutine do Web of Trust
* `db.*`: tuning do pool pgx
* `redis.*`: cache/pubsub e hygiene de subscriptions
* `admin_token`: protecao do plano administrativo interno (`/admin/*` + `/panel`)
* `admin_pubkey` + `nip86.*`: habilitacao e tuning da superficie administrativa externa NIP-86
* `nip29.*`: habilitacao de grupos, admissao, moderacao, convites, PoW, timeline e cache
* `ingestion.*`: throughput vs memoria/latencia
* `cron.*`: jobs de manutencao e retention
* `stream.*`: federacao upstream/downstream
* `enable_negentropy`: habilita mensagens `NEG-*`
* `store.*`: NIP-96 e regras de conteudo

=== 8.4 Modos de autenticacao WS

`ws.auth_mode`:

* `strict`: auth obrigatoria para REQ e EVENT
* `flexible`: auth obrigatoria para EVENT
* `optional`: auth opcional (challenge enviado)
* `none`: auth desligada

Compatibilidade:

* se `auth_mode` invalido e `ws.auth=true`, runtime normaliza para `strict`

== 9. CLI tecnica

=== 9.1 Comandos principais

* `server`: sobe runtime do relay
* `proxy`: edge-router focado em throughput extraindo/deduplicando de varios upstream relays
* `seed`: migracao e bootstrap opcional
* `cron`: scheduler/list/run-once de jobs
* `conf`: print/effective/validate/write
* `import`: ingestao JSONL local
* `export`: dump jsonl/tsv com filtro
* `download`: coleta de relays externos para DB local
* `sync`: reconciliacao Negentropy

=== 9.2 Regras e validacoes relevantes

* `seed --skip-migrate` exige `--bootstrap`
* `seed --bootstrap-idempotent` exige `--bootstrap`
* `cron --list` nao combina com `--run-once`
* `download --mentioned` exige `--public-key`
* `download` aceita apenas uma fonte de filtro (`--filter` ou `--filter-file`)
* `sync` exige relay remoto por argumento posicional ou `--remote`
* `conf validate` falha se `nip86.enabled=true` sem `admin_pubkey` e `relay_information.url`

== 10. Persistencia e modelo de dados

=== 10.1 PostgreSQL

Tabelas chave (ver `docs/data-schema.md` para definicao completa):

* `event`: armazenamento principal de eventos Nostr
* `profiles`: metadados de usuarios
* `banned_users`: moderacao
* `nip86_allowed_pubkeys`, `nip86_banned_events`, `nip86_blocked_ips`, `nip86_relay_metadata`: estado administrativo do NIP-86
* `objects`: metadados de blobs NIP-96
* `nip29_groups`, `nip29_roles`, `nip29_group_roles`, `nip29_group_members`, `nip29_group_bans`, `nip29_group_invites`: estado relacional de grupos NIP-29

Migracao:

* SQL embedado em `infra/db/schema.sql`
* executado por `Queries.Migrate()`

=== 10.2 Redis

Uso quando habilitado:

* cache de ban/profiles/query/event/dedup
* pubsub de eventos e estado distribuido
* cleanup de subscriptions stale
* cache hot-path de metadata, membership, bans, invites e timeline recente de grupos NIP-29

Chaves e canais: ver `docs/data-schema.md`.

== 11. Observabilidade e diagnostico

=== 11.1 Logs

Logger estruturado via Zap.

Pontos de log importantes:

* startup/shutdown de servidores
* falhas de DB e Redis
* erros de write/read WS
* falhas de batch ingestion
* falhas de stream forwarding

=== 11.2 Metricas

Expostas em `/metrics` (servidor interno).

Cobertura principal:

* request types WS
* ingestion (batch, duration, duplicates, errors, backpressure)
* forwarding stream
* Negentropy
* download command metrics por relay
* grupos NIP-29: grupos criados/ativos, eventos recebidos/rejeitados, invites, latencia e hit/miss de cache

== 12. Seguranca e controles

Controles implementados:

* autenticacao NIP-42 por politica configuravel
* validacao criptografica de eventos (id + assinatura)
* limite de tamanho de payload WS
* autenticacao NIP-98 para NIP-86 quando habilitado
* politicas de conteudo (base64 inline)
* controle de acesso admin por token opcional
* politicas para kinds protegidos/DM
* controles opcionais NIP-29 para permissao de grupo, convites, PoW e timeline references

Riscos operacionais a observar:

* `admin_token` vazio em ambiente exposto
* `nip86.enabled=true` sem reverse proxy, governanca operacional ou administracao de chaves adequada
* `ws.auth_mode=none` em relay publico sem mitigacoes de abuso
* retention e cron mal configurados

=== 12.1 Orientacoes para usuarios finais e operadores

Para uso simples/local:

* mantenha `nip86.enabled=false`
* defina `admin_token` se abrir o painel alem de `localhost`
* use apenas PostgreSQL se nao precisar de cache/pubsub distribuido

Para uso avancado/remoto:

* habilite NIP-86 somente se existir necessidade real de automacao remota por tooling Nostr-native
* trate `admin_pubkey` como credencial de alto impacto operacional
* prefira expor a superficie publica atras de TLS/reverse proxy estavel para manter `relay_information.url` consistente
* em clusters, considere coordenacao adicional para disconnect imediato cross-node

== 13. Operacao e manutencao

=== 13.1 Setup minimo (local)

[source,bash]
----
go run ./cmd/nrserver conf write
go run ./cmd/nrserver conf validate
go run ./cmd/nrserver seed
go run ./cmd/nrserver server
----

=== 13.2 Setup com Dockerfile (standalone)

O projeto possui `Dockerfile` multi-stage com:

* build frontend (`infra/dash`) via Node/pnpm
* build backend Go (`cmd/nrserver`)
* imagem final distroless com binario Go estatico e usuario nao-root

Build local da imagem:

[source,bash]
----
docker build -t nostr-relay-server:local .
----

Execucao com arquivo de configuracao local:

[source,bash]
----
docker run --rm \
  -p 9090:9090 \
  -p 9091:9091 \
  -v $(pwd)/conf.yaml:/app/conf.yaml:ro \
  nostr-relay-server:local
----

Notas operacionais:

* o entrypoint da imagem ja executa `nrserver server`
* o processo espera `conf.yaml` montado em `/app/conf.yaml`
* a porta interna admin/metrics/panel continua sendo `port+1`

=== 13.3 Setup com Docker Compose + Tor

Para ambiente com PostgreSQL, Redis e onion service, use os arquivos:

* `docker-compose.yml`
* `deploy/postgres/postgresql.conf`
* `deploy/postgres/password.txt.example`
* `deploy/redis/redis.conf`
* `torrc`
* `stack.yml`

No runtime Docker, `conf.yaml`, `postgresql.conf`, `redis.conf` e `torrc` sao entregues via `configs`, e a senha do Postgres via `secret`.

Fluxo recomendado:

1. criar arquivo local de senha do PostgreSQL:
+
[source,bash]
----
cp deploy/postgres/password.txt.example deploy/postgres/password.txt
----

2. ajustar `conf.yaml` para usar os nomes de servico internos:
+
[source,yaml]
----
db:
  postgres_uri: postgres://postgres:SUA_SENHA@postgres:5432/nostr?sslmode=disable

redis:
  enabled: true
  addr: redis:6379
  password: ""
----

3. subir stack completa:
+
[source,bash]
----
docker compose up -d --build
----

4. obter hostname onion:
+
[source,bash]
----
docker compose exec tor cat /var/lib/tor/nostr-relay/hostname
----

5. atualizar URLs publicas em `conf.yaml` e reiniciar `nrserver`:
+
[source,bash]
----
docker compose restart nrserver
----

Campos tipicos a revisar no `conf.yaml` apos obter o `.onion`:

* `relay_information.url`
* `relay_information.canonical_url`
* `relay_information.icon`
* `store.api_path`
* `store.media_path`

=== 13.4 Setup com Docker Swarm

Para deploy em Swarm use `stack.yml`.

Passos:

1. inicializar o swarm se necessario:
+
[source,bash]
----
docker swarm init
----

2. preparar os mesmos mounts locais usados no compose:

* `./conf.yaml`
* `./deploy/postgres/postgresql.conf`
* `./deploy/postgres/password.txt`
* `./deploy/redis/redis.conf`

3. subir a stack:
+
[source,bash]
----

----

4. acompanhar servicos:

[source,bash]

----

* validar config antes de deploy (`conf validate`)

* usar `cron --list` e `cron --run-once` para validacao de jobs

=== 13.6 Troubleshooting tecnico

Sintoma: `missing DB URI`

* causa: `db.postgres_uri` ausente
* acao: preencher `conf.yaml` e revalidar

Sintoma: `invalid cron expression`

* causa: formato cron incorreto
* acao: usar 6 campos (`sec min hour day month weekday`)

Sintoma: queda de ingestao com drops

* causa provavel: backpressure (fila cheia)
* acao: revisar `ingestion.queue_size`, `workers`, `batch_size` e pressao de entrada

Sintoma: admin retorna 401

* causa: token ausente/invalido
* acao: enviar `X-Admin-Token` quando `admin_token` estiver configurado

== 14. Estrutura de projeto e pontos de extensao

=== 14.1 Pontos de extensao recomendados

* novas politicas: `internal/policies`
* novos jobs cron: `cmd/internal/cron/jobs.go`
* novos endpoints admin: `infra/handler/http/admin.go`
* novos tipos de exportacao: `cmd/internal/export`

=== 14.2 Dependencias entre componentes

* handlers WS delegam validacao ao hub de politicas

* stream depende de `nostrpool` e flags `stream.*`
* cache/pubsub dependem da disponibilidade Redis

== 15. Decisoes tecnicas e trade-offs

Resumo tecnico (ADRs em `docs/decisions.md`):

* Go para concorrencia e deploy simples
* Fiber para throughput HTTP
* PostgreSQL para flexibilidade de consulta/indexacao
* Redis opcional para escalar horizontalmente
* pipeline async (ingestion/stream) para proteger hot-path WS

Trade-offs percebidos no codigo:

* maior complexidade operacional em troca de throughput e resiliencia
* validacoes mais estritas reduzem ambiguidade, mas exigem melhor configuracao
* acoplamento moderado entre handlers e camadas infra ainda existe em alguns fluxos legados
